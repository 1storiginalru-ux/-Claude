# Продажи WB/Маркета и показатели негатива

Продажи WB загружаются из API статистики. Для Маркета добавлены API заказов
и статистики: [подключение АМ/ЕС/ОП и ограничения дат](YANDEX_SALES.md).
Включение API выполняется отдельно; прежние CSV сохраняются без повторного подсчёта.

## Стойкость и оригинальность

В фильтрах, карточках и аналитике одна группа — **Стойкость и оригинальность**
(`LONG_AUTH`). Она включает `LONG`, `AUTH` и все подтипы `AUTH-*`.
Один отзыв с несколькими такими метками учитывается в группе один раз.

Исходная разметка сохраняется: это позволяет оператору различать причины и
применять Human Only к сомнениям в оригинальности. Объединение не включает
автоматическую публикацию ответа. Старые расследования и пороги AUTH/LONG
сохраняются. Для новой группы нужен собственный baseline: старые проценты
не складываются. Исторический расчёт считает объединение уникальных отзывов.

## Источник продаж

Используется `GET https://statistics-api.wildberries.ru/api/v1/supplier/sales`,
`flag=0`, с продолжением по полному `lastChangeDate`. Контракт сверён с моделями
`SalesItem` и описанием метода из `wildberries-sdk@0.1.174`, ранее загруженного
из публичного npm. Официальный раздел: https://dev.wildberries.ru/openapi/reports.
Реальный доступ и соответствие отчёту продавца проверяются на вашем сервере.

- Одна строка — одна единица товара. `S…` означает продажу, `R…` — возврат.
- Сохраняются `saleID`, `srid`, `nmId`, даты операции/изменения и полный JSON.
- Уникальность — кабинет + `saleID`. Повтор страницы не увеличивает продажи;
  исправление обновляет запись. Более старая версия не заменяет новую.
- Связь с ProductID — по кабинету и артикулу WB `nmId`.
- Возврат хранится отдельно, первоначальный выкуп не удаляется.
- Отчёт оперативный: WB обновляет его примерно раз в 30 минут и предупреждает
  о возможных отличиях от финансовых отчётов, включая неподтверждённые оплаты.
  Цена 0 не является основанием выкидывать продажу: поля заполняются асинхронно.

Для нового цикла текущего опроса `dateFrom` ограничен последними 7 сутками.
Это фильтр даты изменения WB; строки дополнительно фильтруются по дате операции.
Отдельная загрузка истории расширяет период до 14/30/60/90 дней, чтобы собрать
последние 100 выкупов каждого товара по всем кабинетам. Накопленная локальная
история остаётся. [Порядок загрузки и ограничения](HISTORY.md).

Один проход poller получает одну страницу. Позиция страницы и пауза сохраняются
в отдельном состоянии. Полнота подтверждается только после пустого массива,
как описывает WB. Успешное получение одной непустой страницы ещё не означает
полный период. Продолжение не чаще минуты; после полного цикла — через 30 минут
с учётом фактического API-бюджета. Бюджет статистики отделён от отзывов.
При 429 учитываются заголовки, а без заголовков используется консервативная
пауза для базового токена. Лимиты различаются по типам токенов; повторные ручные
команды их не обходят.

## Включение на Beget

Сначала обновите остановленные службы с резервной копией:

```bash
systemctl stop voice-web voice-worker voice-poll
voice-manage backup_db
cd /opt/voice
git pull --ff-only
bash deploy/install.sh
systemctl enable --now voice-worker voice-poll
```

Миграция `0006` добавляет таблицы событий и покрытия; `0008` — очередь
исторической загрузки. Существующие отзывы, разметка, сопоставления,
история публикаций и ключи сохраняются.
Продажи по умолчанию выключены. В Voice откройте **Интеграции → ВБ_1 →
Настроить кабинет**, включите **Получать продажи через API (WB / Маркет)** и сохраните.

Пустое поле **Переменная отдельного ключа продаж** использует текущий
ключ кабинета. Если у него нет доступа, в результате появится ошибка прав.
Можно создать отдельный ключ WB с категорией **Статистика** и правом чтения,
сохранить на сервере:

```bash
voice-set-key VOC_WB_STATS_TOKEN
```

В настройках кабинета укажите `VOC_WB_STATS_TOKEN` в поле отдельной переменной
и перезапустите `voice-web` и `voice-poll`. Не меняйте ключ отзывов для этой цели.
Ключи в чат не присылаются. Демо и отключённые кабинеты не опрашиваются.

Чтение состояния без сетевых запросов:

```bash
voice-manage sales_status --account ВБ_1
```

Один явный проход с соблюдением пауз:

```bash
voice-manage sync_sales --account ВБ_1
```

Фоновая работа уже встроена в `voice-poll`, второй процесс не нужен.
Один и тот же кабинет продавца не следует подключать как несколько независимых
источников продаж под разными Account.

## Сверка трёх товаров

Выберите три существующих артикула WB: с частыми продажами, с редкими продажами
и с возвратом, если такой есть. Подставьте реальные nmId вместо примеров:

```bash
voice-manage sales_status --account ВБ_1 --sku 123 --sku 456 --sku 789
```

Команда выводит границы периода в UTC. В интерфейсе Voice даты показываются
в московском времени. В кабинете продавца используйте тот же тип оперативного
отчёта и тот же период, учитывая неполные граничные дни и задержку обновления.
Сверяйте выкупы и возвраты отдельно. Затем проверьте в карточке товара:
ProductID, артикул/кабинет, список выкупов и источник данных.
Сначала дождитесь сообщения о полном периоде. До реальной сверки не считаем
точность внешнего источника подтверждённой одними контрактными тестами.

## Окна и проценты

В карточке можно выбрать отдельный кабинет, в том числе только WB, пока продажи
Маркета не подключены. По отдельным событиям WB и Маркета окно выбирает ровно последние
100 единиц. Если выкупов меньше, показывается фактическое число и предупреждение.
Если участвуют дневные агрегаты, включается целиком граничный день: знаменатель
может быть больше 100. API-события и CSV одного кабинета не складываются:
при включённых API-продажах используется источник API, CSV остаётся в базе.

Для отдельных API-событий отзывы и продажи берутся на общий момент последнего
полностью загруженного периода, показанный в карточке. Незавершённое обновление
не подмешивает более свежие данные в старый полный снимок.
При пробеле в истории, устаревании более трёх часов или отсутствии данных
одного из кабинетов показатель помечается неполным. Старая база после миграции
не объявляется автоматически полной: покрытие подтверждают последующие циклы.
Если семидневного периода недостаточно для 100 выкупов медленного товара,
отдельная очередь автоматически расширяет запросы, максимум до 90 дней.
Отзывы за тот же период догружаются отдельно. До завершения этого обхода
полнота не подтверждена. Для редкого товара 100 выкупов может не найтись.

Показатели различаются:

| Показатель | Формула |
|---|---|
| Негатив среди отзывов | Уникальные негативные отзывы / все отзывы окна × 100% |
| Негатив на 100 выкупов | Уникальные негативные отзывы окна / выкупленные единицы окна × 100 |

Пять негативных отзывов из двадцати при ста выкупах означают 25% среди отзывов
и 5 негативных отзывов на 100 выкупов. Второй показатель не определяет долю
недовольных покупателей: индивидуальная связь отзыва с покупкой не гарантирована.
Вопросы и ответы продавца в эти два показателя не входят.

Негатив — отрицательная тональность либо скрытый негатив. Для основного числа
нужна разметка с уверенностью от 0.7. Правила по ключевым словам, демо, отсутствие
анализа и низкая уверенность требуют проверки; это не положительные отзывы.
Отдельно видна доля среди разобранной части. Полные показатели не показываются
при неподтверждённой полноте соответствующего источника или неполной разметке.
Доля негатива за фиксированные 7 дней может рассчитываться без продаж, если
отзывы и классификация за период полны. Ноль отзывов не даёт процент среди
отзывов; при полном покрытии и ненулевых продажах он даёт ноль сигналов на 100.

Порог классификации требует проверки на реальных примерах. Если AI не подключён,
предварительная разметка остаётся видимой, а достоверные проценты будут ждать
разбора. Настройка AI и проверка черновиков выполняются отдельным этапом.
Для отдельного кабинета общий baseline товара не применяется; его raw-показатели
можно сравнить вручную. Кластер подтверждённых жалоб и тяжёлый объективный случай
по-прежнему могут требовать внимания без достаточной выборки продаж.

Ручная проверка отзывов, приоритетная очередь и включение правил общего негатива:
[Контроль товаров и расследования](CONTROL_WORKFLOW.md).

## Основание проверки и решение оператора

«Контроль товаров» считает учтённые негативные отзывы: по актуальному решению
сотрудника либо AI-разметке с уверенностью не ниже 0,7. Предварительная разметка
по словам (`rules`), демо и низкая уверенность не запускают автоматическое
расследование серьёзной проблемы. Ручная эскалация сотрудником остаётся доступной.

В карточке отзыва различаются состояния «Оператор ещё не проверял», «Решение
отложено», «Подтверждено сотрудником» и «Нужна повторная проверка». Начальные значения
несохранённой формы не являются решением. До сохранения может использоваться AI;
сохранённое «Требует проверки» исключает отзыв из учтённой разметки до пересмотра.
Подтверждение негатива фиксирует наличие жалобы, а не достоверность обвинения.

Для новых расследований снимок хранит отдельно событие открытия (порог, серия,
серьёзная проблема или ручная эскалация), обращение, кабинет и источник разметки.
Показатели в окне сохраняются отдельно: ноль в счётчике не означает отсутствие
связанного обращения. Оно могло быть вне тогдашнего окна или ещё не учитываться.
Старые снимки не переписываются и не получают выдуманного основания: интерфейс
явно сообщает, если историческое основание отдельно не сохранялось.

Последующее изменение разметки не закрывает расследование автоматически. Вывод,
ответственного, срок и результат проверки фиксирует сотрудник. Обновление не
меняет настроенные пороги и не запускает платный разбор накопленных отзывов.

## Постоянное накопление и подтверждение продаж

SaleEvent — постоянный журнал отдельных выкупленных и возвращённых единиц,
с уникальностью кабинет + внешний ID. Повторные опросы не удваивают события;
поздние исправления старых выкупов WB сохраняются по свежему lastChangeDate.
Для Маркета сохраняются версии заказов, неопределённые количества/даты и аудит
исправлений. Возвраты учитываются отдельно от исходных выкупов.

Первый текущий запрос охватывает 7 суток. Последующие начинают с последнего
подтверждённого момента минус 6 часов, с ограничением текущего запроса неделей.
Это перекрытие для запоздавших изменений, а не удаление старой базы. Исторический
поток отдельно дозагружает недостающие периоды, максимум на 90 дней назад.
Страницы текущих продаж завершаются приоритетно перед расширением истории.
Реальные паузы WB и Маркета не сбрасываются и не обходятся.

Для WB после успешно проверенной страницы сохраняется подтверждённый префикс
до lastChangeDate последней строки **минус одна микросекунда**. Граничный момент
исключён: за ним могут оставаться непрочитанные записи с тем же временем.
Полный обход по-прежнему подтверждается только завершением пагинации. Ошибочная,
непродвигающаяся страница или потерянная lease не подтверждает новый интервал.
Завершённые API-интервалы записываются в Audit с действием `sales.coverage`.

В показателях различаются три состояния:

- Итоговое значение: окно покрыто, разметка полна, данные свежие.
- Подтверждённый снимок на указанный момент: тот период полон, но обновление отстаёт.
- Предварительное значение по загруженным данным: часть данных или разметки отсутствует.

Последнее подтверждение старше трёх часов больше не называется пробелом истории:
показывается отдельная причина устаревания. Подтверждённые события не теряются при
паузе API. Исторический и предварительный показатели подписаны и не используются
для автоматического процентного срабатывания свежего окна. Серии жалоб и серьёзные
конкретные случаи продолжают проверяться отдельно. Неопределённые исходные выкупы
Маркета блокируют окончательную оценку только затронутых SKU и периодов; даты
таким заказам не придумываются.
