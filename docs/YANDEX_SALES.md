# Автоматические продажи Яндекс Маркета

## Что подключается

Продажи Маркета поступают через API заказов и статистики. По вашему текущему
плану включаются ЯМ_1 (АМ), ЯМ_2 (ЕС), ЯМ_3 (ОП). Команда включения не меняет
Velato, WB или Ozon. Само обновление схемы не включает новые источники.

В API используются:

- `POST /v1/businesses/{businessId}/orders`: реальные заказы, состав, количества,
  индивидуальные статусы единиц, дата изменения и принадлежность магазину.
- `POST /v2/campaigns/{campaignId}/stats/orders`: состояние и дата смены статуса.
  Магазины определяются из заказов выбранного Business ID. Не нужно вручную
  вводить Campaign ID или собирать заказы по каждому SKU.

Заказы опрашиваются по дате обновления, включая отмены и изменения старых
заказов. На страницу — до 50 заказов. Статистика запрашивается по их ID отдельно
для каждого магазина; товары и услуги из статистики не складываются с составом
заказа. Позиции доставки и услуг не увеличивают количество купленных товаров.

## Как считаются выкупы

Одна единица товара — одно событие продажи, даже если в заказе их несколько.
Связь с товаром: кабинет + `offerId` → общий ProductID.

При наличии `itemStatuses` учитываются `DELIVERED_TO_BUYER` и `RETURNED`:
возвращённый товар сначала был выкуплен. `REJECTED`, `CANCELLED`, `LOST`,
`SHIPPED`, `CREATED` не считаются выкупами. Без статусов единиц весь `count`
принимается только для полностью доставленного или полностью возвращённого
заказа. Частичный возврат без достаточных количеств остаётся неподтверждённым.
`PICKUP` означает доставку в ПВЗ, а не получение покупателем.

Подтверждённая дата выкупа — `statusUpdateDate` статистики в состоянии
`DELIVERED`. Для строки с количеством N создаются N устойчивых идентификаторов.
API называет это датой изменения статуса заказа; это оперативная дата фиксации
получения, а не момент оплаты каждой отдельной единицы.

При последующем возврате ранее известная дата выкупа сохраняется. Возврат
хранится отдельным событием и не уменьшает знаменатель 100 выкупленных единиц.
Даты возвратов — даты подтверждения статуса; они не заменяют дату финансовой
операции и не участвуют в выборе последних выкупов.

### Когда точная дата неизвестна

Если заказ впервые получен уже в `RETURNED`/`PARTIALLY_RETURNED`, последняя
дата статуса может относиться к возврату. Она не выдаётся за дату исходного
выкупа. Если количество либо дата не подтверждены, сохраняется отдельная
неопределённая позиция, а проверенные прежние события не удаляются.
Неизвестный новый статус также не обнуляет ранее доказанные выкупы.

В карточке товара появится блок **Неподтверждённые выкупы Маркета** с кабинетом,
заказом, артикулом и причиной. Если возможная дата такого выкупа пересекает
текущее окно, достоверные проценты скрываются. Другие товары и более свежие
окна, на которые неопределённость не влияет, продолжают рассчитываться.
Поэтому автоматическая загрузка не гарантирует точный процент для любой
старой истории: часть возвращённых заказов может потребовать сверки.

Статистика Маркета может отставать до 40 минут. Если заказ ещё отсутствует в
статистике или версии расходятся, страница откладывается; покрытие не становится
полным. Даты доставки в ПВЗ, оформления и получения ответа API не подставляются
вместо подтверждённой даты выкупа.

## Дедупликация и полнота

Каждая версия заказа сохраняется отдельно от событий единиц. Старый ответ не
заменяет новую версию. Уменьшение количества, удаление позиции или отмена
исправляют события заказа, а повтор страницы не увеличивает продажи.
Некорректная страница не записывается частично. Одновременные текущая и
историческая загрузки используют общую блокировку кабинета.

Текущий цикл — изменения за 7 суток. История при необходимости расширяется
на 14 → 30 → 60 → 90 суток, с интервалами запросов не более 30 суток и
сохранением страниц. Полнота запросов и достоверность дат/количеств — разные
проверки: завершённый обход не скрывает неподтверждённые позиции.

Общий ProductID объединяет отдельные события WB и Маркета: окно выбирает ровно
последние 100 известных единиц по всем источникам. CSV того же кабинета при
включённом API не прибавляется, но остаётся в базе. Отзывы догружаются за тот же
период. Права на другие компании не расширяются.

## Установка и включение

В SSH-окне сервера:

```bash
systemctl stop voice-web voice-worker voice-poll &&
voice-manage backup_db &&
cd /opt/voice &&
git pull --ff-only &&
bash deploy/install.sh &&
voice-manage enable_market_sales --apply &&
systemctl enable --now voice-web voice-worker voice-poll
```

`enable_market_sales` без `--apply` выполняет проверку. Команда использует точные
имена ЯМ_1/ЯМ_2/ЯМ_3 и юрлица АМ/ЕС/ОП, проверяет наличие Business ID и ключей.
Изменения атомарны и повторяемы. Один Business ID не может включаться повторно
в нескольких источниках продаж. Velato остаётся без изменений.

Миграция `0010` добавляет состояние заказов и общие названия настроек продаж;
WB-события, курсоры, паузы, CSV, сопоставления, отзывы и опубликованные ответы
сохраняются. Исторические и текущие позиции отзывов Маркета не сбрасываются.

## Права ключа и диагностика

Ключ отзывов может не иметь прав заказов. Нужны разрешения чтения заказов и
статистики (например, `inventory-and-order-processing:read-only` либо общий
ключ чтения). Права `communication` сами по себе недостаточны для этих методов.
Проверка без отправки запросов:

```bash
voice-manage sales_status --account ЯМ_1
voice-manage history_status --account ЯМ_1
voice-manage diagnose_ym_sales --account ЯМ_1
```

Проверка доступа к заказам и, при наличии заказа, его статистике без импорта:

```bash
voice-manage diagnose_ym_sales --account ЯМ_1 --probe
```

Все запросы чтения, без изменения заказов, статусов и ответов покупателей.
HTTP 420/429, Retry-After и растущая пауза сохраняются в БД. Бюджет продаж
Маркета отделён от WB и опроса отзывов. Ручной запуск не обходит паузы.

При недостаточных правах можно выдать отдельный ключ чтения заказов:

```bash
voice-set-key VOC_YM_SALES_TOKEN
```

В настройках нужного кабинета укажите `VOC_YM_SALES_TOKEN` в поле
**Переменная отдельного ключа продаж**, затем перезапустите три службы.
Для ЕС/ОП используйте отдельные имена переменных и ключи соответствующего бизнеса.
Ничего не меняйте в ключах уже работающих отзывов, если используете отдельный ключ.

Запуск одной страницы с соблюдением пауз:

```bash
voice-manage sync_sales --account ЯМ_1
```

## Проверка на реальном кабинете

После первого завершённого цикла выберите три артикула: обычный, с несколькими
единицами в заказе и с возвратом. Сверьте по одним датам и статусам:

```bash
voice-manage sales_status --account ЯМ_1 --sku ARTICLE1 --sku ARTICLE2 --sku ARTICLE3
```

Отдельно сравнивайте выкупы и возвраты; не сравнивайте валовые выкупы с чистым
итогом «продажи минус возвраты». Оперативный API не заменяет финансовую сверку.

Контракты проверены по официальным схемам
[заказов](https://github.com/yandex-market/yandex-market-partner-api/blob/main/openapi/paths/v1_businesses_businessId_orders.yaml),
[статистики](https://github.com/yandex-market/yandex-market-partner-api/blob/main/openapi/paths/v2_campaigns_campaignId_stats_orders.yaml)
и `OrderItemUnitStatusType`. Проверки среды разработки используют контролируемые
ответы. Доступ и фактические числа продавца проверяются после установки на VPS.
