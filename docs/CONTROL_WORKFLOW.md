# Контроль товаров и ручная проверка отзывов

## Работа оператора

Откройте отзыв из Inbox или из «Контроль товаров → Ждут разметки».
Блок «Решение оператора» позволяет выбрать «Негатив», «Не негатив» или
«Требует проверки», причины, важность и комментарий. Оператор, руководитель,
сотрудник качества и расследований могут подтверждать отзывы своей компании;
роль просмотра не может изменять данные. Исходный AI-анализ остаётся отдельно.

- Подтверждённое решение сотрудника имеет приоритет над AI, в том числе после
  повторного AI-анализа. Для работы этой функции AI-ключ не требуется.
- «Требует проверки» не считается положительным отзывом: расчёт частоты остаётся
  неполным. Решение по вопросу покупателя не входит в показатели отзывов.
- Изменение текста, оценки, артикула или ProductID делает прошлое решение
  устаревшим. Сотрудник должен проверить новую версию. Изменения лайков, фото,
  ответов продавца и другой метаинформации не сбрасывают решение по тексту.
- Защита версии формы не позволяет затереть решение другого сотрудника или
  подтвердить текст, который успел измениться. Изменения сохраняются в аудите.
- Стойкость и оригинальность — одна причина. Отзыв с несколькими причинами
  учитывается в общем негативе один раз. Подтверждённый «Не негатив» не попадает
  и в счётчики жалоб по темам, даже если темы оставлены для контекста.
- AI/правила продолжают работать как раньше; предварительные правила по словам
  не являются подтверждённой разметкой. Порог доверия AI остаётся 0.7.

## Очередь товаров

Пункт меню «Контроль товаров» открывает `/voc/`. Одна строка — один физический
ProductID по компаниям, к которым у сотрудника есть доступ. Очередь включает
товары с отзывами без анализа, не только успешно разобранные AI.

Показаны окно выкупов, подтверждённый негатив, частота на 100, причины, момент
данных, неразобранные отзывы и открытые расследования с ответственным/сроком.
Фильтры: требуют внимания, есть расследование, ждут разметки, недостаточно данных.
Сортировка всех подходящих товаров выполняется **до** разбиения на страницы:
аномалии, открытые расследования, предупреждения, неполные данные, ненастроенные
пороги, обычный уровень. Открытие очереди не создаёт инциденты и не меняет базу.
Данные загружаются пакетно, количество запросов не растёт на каждый товар.

Из строки можно перейти в карточку товара, в связанные расследования или в
точную выборку непроверенных отзывов этого ProductID за семь дней.

Общие показатели не заменяют контроль отдельных кабинетов. Для каждого кабинета
применяется такое же правило **в его собственном окне 100 выкупов**. Утверждать
массовую проблему по проценту при 1 жалобе на 10 выкупов нельзя. Сравнение
кабинетов в одном общем календарном периоде пока выполняется по выгрузке;
окна по количеству в каждом кабинете могут иметь разную глубину.

## Включение правила

В карточке товара найдите «Правило общего негатива → Настроить пороги и серию
жалоб». Роль руководителя/качества/расследований должна иметь доступ ко всем
компаниям данного физического ProductID; superuser может настраивать любой товар.

Начальное предложение: предупреждение от 5, расследование от 10, минимум
100 выкупов и 3 негативных отзыва. Это стартовые настройки, а не установленная
статистическая норма. Сохранение включает правило данного товара. До сохранения
показывается «Пороги не настроены», отсутствие правила не означает норму.

Порог включает равенство: ровно 10 на 100 при пороге 10 создаёт расследование.
Сравнение проводится по полной точности, округление используется только на экране.
Для процентного правила нужны полные продажи, отзывы и классификация окна.
Дневные файлы включают весь граничный день, поэтому знаменатель может превышать 100.
Возвраты хранятся отдельно и не вычитаются из знаменателя частоты жалоб.

Альтернативное правило — минимум похожих жалоб за заданное количество дней.
Для общего негатива серия должна иметь общую товарную тему; четыре жалобы по
четырём разным причинам не объявляются кластером. Подтверждённая серия может
сработать при недостаточном числе выкупов, но процент тогда не показывается.

Правило хранится как ручной Baseline с сигналом `NEGATIVE`. Существующие
пороги отдельных тем сохраняются; старые AUTH/LONG автоматически не складываются
и не создают два новых дела вместо объединённого LONG_AUTH.

## Расследование

Фоновый `sync_channels --loop` после опроса источников повторяет проверку правил,
даже если новый AI-анализ не запускался: продажи, полнота и границы времени
могли измениться. Проверка после решения оператора также выполняется сразу.
Доступные метрики учитывают общий момент полностью загруженных данных; совсем
новый отзыв может войти в процент после следующего завершённого цикла источника.

При срабатывании одно открытое дело на ProductID + причину получает связанные
подтверждённые отзывы. Для `NEGATIVE` контролируются общая частота и каждый
кабинет отдельно: общий объём не должен скрывать локальную проблему.
Серьёзный конкретный случай по-прежнему может эскалироваться без знаменателя.

Снимок при открытии сохраняет счётчики, период с часовым поясом, порог, причину,
кабинет (если сработал он) и неполноту данных. Он не переписывается при изменении
продаж, отзывов или настроек. Старые расследования показывают, что снимка нет;
исторические числа не выдумываются. Полный снимок другой компании не раскрывается
сотруднику с частичным доступом; связанные отзывы также ограничены его правами.

В карточке руководитель/качество/расследования выбирает ответственного из
доступных сотрудников, срок по Москве, статус, гипотезу, действия и результат.
Статусы: «Проверка», «Принимаем меры», «Контроль», «Закрыто». Изменение версии
защищает от одновременной перезаписи; при закрытии обязателен результат.

Падение показателя не закрывает случай автоматически. Закрытое дело не открывается
каждую минуту по тем же отзывам; для нового автоматического дела нужны новые
свидетельства. Число в карточке товара при этом может оставаться выше порога,
пока прежние отзывы не выйдут из скользящего окна.

Новая фоновая проверка не публикует ответы и не передаёт задачи наружу. Ручная
работа с Bitrix24 сохраняется отдельным действием при настроенном подключении.

## Обновление сервера

В терминале сервера от root, по одной команде; при ошибке остановиться:

```bash
systemctl stop voice-web voice-worker voice-poll
voice-manage backup_db
cd /opt/voice
git pull --ff-only
bash deploy/install.sh
systemctl enable --now voice-worker voice-poll
systemctl is-active voice-web voice-worker voice-poll
```

Миграция `0007` добавляет ручные решения и снимок. Отзывы, исходный анализ,
опубликованные ответы, сопоставления, продажи, паузы WB и ключи сохраняются.
Новые пороги не включаются массово: начните с одного товара и проверки его отзывов.
Продажи Маркета остаются через файл; продажи Ozon в этой версии не подключены.

Исправление ложного скрытого негатива и автоматический пересчёт старых правил:
[Разметка жалоб](CLASSIFICATION.md).

## Общие пороги для кабинетов

Команда `configure_control` сохраняет общее правило для явно выбранных кабинетов.
Оно применяется к текущим и новым сопоставлениям ProductID без своего правила.
Отдельный Baseline товара (ручной или исторический) имеет приоритет и не меняется.
Правило относится к общему негативу; существующие тематические правила сохраняются.
В интерфейсе источник обозначен «Общее правило кабинетов». Сохранение формы в
карточке товара создаёт отдельное правило этого ProductID.

Стартовые параметры: предупреждение **от 5**, расследование **от 10** негативных
отзывов на 100 выкупов, минимум **100 выкупов** и **3 негативных отзыва**.
Отдельный триггер — **4 однотипные жалобы за 3 дня**, даже при недостатке продаж.
Это начальная рабочая настройка, которую следует оценивать по реальным случаям.

Для трёх магазинов (АМ, ЕС, ОП), в серверной консоли root:

```bash
voice-manage configure_control --account ВБ_1 --account ЯМ_1 --account ВБ_2 --account ЯМ_2 --account ВБ_3 --account ЯМ_3
voice-manage configure_control --account ВБ_1 --account ЯМ_1 --account ВБ_2 --account ЯМ_2 --account ВБ_3 --account ЯМ_3 --apply
```

Первая команда — просмотр, вторая сохраняет. До записи создаётся JSON-копия
прежних настроек с правами 0600 в каталоге backups. Повтор той же команды не
создаёт дубли и не меняет отдельные правила товаров. Для других значений есть
`--warning`, `--threshold`, `--min-signals`, `--cluster-count`, `--cluster-days`.
Velato, Ozon и неуказанные кабинеты не подключаются к общему правилу.

В объединённом ProductID применяются одинаковые общие настройки участвующих
выбранных кабинетов. Если они различаются, общее правило не выбирается произвольно:
нужно задать отдельное правило товара; проверки кабинетов сохраняют свои пороги.
Данные и правила другой компании не раскрываются пользователю без доступа.

Миграция 0016 добавляет только таблицу общих настроек, без включения правил и
изменения существующих данных. Сам `--apply` не запускает AI, отправки или
расследования. После сохранения правила подхватываются обычной фоновой проверкой.
Полнота продаж, разметка отзывов и приоритет решения сотрудника продолжают
проверяться: настройка порогов не превращает неполные показатели в достоверные.

## Тематические пороги кабинетов

Миграция `0019` добавляет `ControlTopicRule` и явное различие между историческим
диапазоном Baseline и бизнес-порогами. Миграция не включает профиль и не создаёт
проверок. Существующие значения индивидуальных правил сохраняются; общий негатив
помечается как правило предупреждения/расследования без изменения его чисел.

Профиль `control-topics-1` включается явно для выбранных кабинетов:

| Тема | Предупреждение от | Расследование от |
|---|---:|---:|
| Общий негатив | 5 | 10 |
| Стойкость и оригинальность | 3 | 5 |
| Аромат | 4 | 7 |
| Упаковка | 2 | 4 |
| Дефект | 1 | 2 |
| Маркировка | 1 | 2 |
| Возврат из-за проблемы | 3 | 5 |
| Описание товара | 2 | 4 |
| Доставка | 3 | 6 |
| Обслуживание | 2 | 4 |
| Цена | 5 | 10 |
| Другая причина | 3 | 6 |

Это негативные отзывы на 100 подтверждённых выкупов, не доля недовольных
покупателей и не фактическая доля возвратов. Границы бизнес-порогов включительные,
сравниваются неокруглённые значения. Минимум жалоб — меньшая из величин 3 и
нижнего порога: для дефекта/маркировки 1, для упаковки/описания/сервиса 2,
для остальных тем 3. Минимальная выборка для процентного правила — 100.

Дефект и маркировка: серия 3 за 7 дней. Стойкость/оригинальность, аромат,
упаковка, возврат и описание: 4 за 3 дня. Общий негатив сохраняет 4 жалобы
на одну из этих тем за 3 дня. Для цены, другой причины, доставки и обслуживания
в стартовом профиле отдельные серии выключены — работают согласованные пороги
частоты. Серии считаются по отдельным негативным отзывам и датам, независимо
от полноты продаж. Недостоверная разметка, будущие отзывы и положительные
упоминания темы не образуют серию.

Индивидуальный Baseline товара имеет приоритет над правилами кабинетов. Старые
исторические диапазоны сохраняют прежнюю интерпретацию; новый Baseline с видом
`thresholds` использует предупреждение и включительный порог расследования.
Одинаковые правила участвующих кабинетов применяются в сводной карточке.
При различии настроек сводное правило не выбирается произвольно: каждый кабинет
всё равно проверяется отдельно по каждой теме. Новые сопоставления товаров
наследуют правила кабинета без массового создания Baseline.

Страница **Контроль товаров → Пороги по кабинетам** (`/voc/rules/`) показывает
12 тем для выбранного доступного кабинета. Руководитель и качество могут менять
порог своей компании; операторы и наблюдатели читают настройки. Версия формы
защищает от перезаписи чужих правок. Несохранённые начальные значения помечены
«Не включено». Общий негатив на этой странице сохраняет проверку серий;
флажок позволяет выключить серию для отдельных тем.

Предпросмотр перед включением, в серверной консоли root:

```bash
voice-manage configure_control_profile \
  --account ВБ_1 --account ЯМ_1 --account ВБ_2 \
  --account ЯМ_2 --account ВБ_3 --account ЯМ_3 --report
```

Команда вычисляет текущий и предлагаемый список внимания, показывает первые
20 товаров и сохраняет полный JSON-отчёт в `STATE_DIR/exports` с правами 0600.
Отчёт включает кабинет, тему, счётчики, причину срабатывания и IDs отзывов,
а также сохранённые индивидуальные правила. Для другого размера вывода есть
`--limit` (1–1000). Список отражает момент расчёта, данные продолжат обновляться.
Предпросмотр не меняет базу, не создаёт расследований и не вызывает внешние API.

Добавление `--apply` сохраняет профиль после вычисления предпросмотра. До записи
создаётся закрытая JSON-копия прежних правил в backups, затем изменения
фиксируются одной транзакцией и аудитом. Если общие пороги кабинетов изменились во время расчёта,
сохранение останавливается. Повторный запуск совпадающего профиля не дублирует
правила и аудит. Команда не меняет Baseline, решения сотрудников, черновики,
AI-задачи или бюджеты и не создаёт исходящих сообщений. Неуказанные кабинеты,
Velato и Ozon не подключаются к профилю.

После включения обычная фоновая проверка рассматривает темы сводно и по каждому
кабинету. Доставка и обслуживание помечаются как контроль процесса кабинета.
Один доверенный отрицательный отчёт P0 или P1 с конкретной проблемой может открыть
проверку без знаменателя. В карточке назначается ответственный. Старые дела
не закрываются автоматически и не открываются заново только из-за тех же
свидетельств; новый серьёзный отзыв может создать новое дело после закрытия.
Стартовый профиль следует оценить через месяц по числу полезных и ложных тревог.
