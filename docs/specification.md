# Техническое задание  
## Единая система клиентских коммуникаций и Voice of Customer

**Версия:** 1.1  
**Назначение:** создание единой программной системы для двусторонней коммуникации с клиентами, AI-обработки обратной связи, контроля клиентского сервиса, накопления истории по товарам и автоматического выявления системных проблем.

Документ предназначен в том числе для разработки с использованием AI-assisted / vibe coding через ChatGPT, Claude, Cursor и аналогичные инструменты.

---

# 1. Бизнес-контекст

Компания продаёт:

- оригинальную парфюмерию через несколько юридических лиц;
- собственный парфюмерный бренд;
- товары одновременно через несколько маркетплейсов и кабинетов.

Используются около 10 торговых кабинетов:

- Wildberries;
- Яндекс Маркет;
- Ozon;
- отдельные кабинеты собственного бренда на маркетплейсах.

Дополнительные каналы коммуникации:

- Telegram;
- WhatsApp;
- MAX.

Один физический товар может одновременно продаваться в нескольких кабинетах и иметь разные:

- SKU;
- offerId;
- артикулы продавца;
- артикулы маркетплейса.

При этом с точки зрения анализа качества это должен считаться **один и тот же физический товар**.

---

# 2. Главная цель системы

Создать единое рабочее пространство, в котором можно:

> получить сообщение клиента → понять контекст → связать его с товаром и заказом → проанализировать AI → увидеть историю товара и статистику проблем → подготовить ответ → отправить ответ обратно клиенту в исходный канал → определить, является ли проблема нормальным фоном или аномалией → при необходимости запустить внутреннее расследование.

Система должна решать одновременно две задачи.

### 2.1. Клиентский сервис

Обеспечивать быструю и качественную двустороннюю коммуникацию с покупателями.

### 2.2. Voice of Customer

Превращать большой поток:

- отзывов;
- вопросов;
- чатов;
- претензий;
- возвратов;

в структурированные данные для улучшения:

- товара;
- поставщиков;
- упаковки;
- логистики;
- карточек товаров;
- сервиса;
- процессов компании.

---

# 3. Основной принцип архитектуры

Система должна быть не просто агрегатором входящих сообщений.

Она должна быть:

> **Unified Customer Communication & Voice of Customer Platform**

То есть поддерживать **полноценную двустороннюю работу**:

**Клиент → площадка → система → оператор/AI → система → площадка → клиент.**

Оператор не должен для обычной работы переходить в кабинеты маркетплейсов.

---

# 4. Поддерживаемые каналы

Система должна иметь интеграции через официальные API, webhooks или polling с:

### Маркетплейсы
- Wildberries;
- Яндекс Маркет;
- Ozon.

### Мессенджеры
- Telegram;
- WhatsApp;
- MAX.

Архитектура должна позволять в дальнейшем добавлять новые источники без переписывания всей системы.

- ответы продавца на отзывы;

- системные сообщения;
- дальнейшие ответы клиента.

# 6. Обязательная двусторонняя коммуникация

Это является **критическим функциональным требованием**.

Система должна не только получать информацию, но и позволять отвечать клиенту непосредственно из единого интерфейса.

Пример:

Клиент пишет в Wildberries:

> «Почему флакон отличается от того, который у меня был раньше?»

Система должна:

1. получить сообщение;
2. определить Wildberries и конкретный кабинет;
3. определить товар;
4. выполнить AI-анализ;
5. показать оператору историю коммуникации;
6. сформировать AI-черновик;
7. позволить оператору изменить его;
8. после нажатия «Отправить» передать сообщение через API Wildberries;
9. клиент должен увидеть ответ непосредственно в Wildberries;
10. дальнейший ответ клиента должен снова появиться в той же цепочке внутри системы.

Аналогично:

**Telegram → система → ответ оператора → Telegram.**

**Яндекс Маркет отзыв → система → ответ → ответ опубликован под отзывом на Яндекс Маркете.**

# 7. Требования к исходящим сообщениям

Для каждого отправленного сообщения хранить:

- внутренний ID;
- внешний ID;
- channel;
- account;
- threadId;
- reviewId / questionId, если применимо;
- sender;
- время формирования;
- время отправки;
- delivery status;
- текст;
- вложения;
- AI draft;
- итоговый текст оператора.

Статусы:

`Draft → Queued → Sending → Sent → Confirmed → Failed`

При ошибке API:

- сообщение не должно теряться;
- оно должно попадать в retry queue;
- должна сохраняться причина ошибки;
- должна поддерживаться ручная повторная отправка.

# 10. Распределение между операторами

Поддержать:

- автоматическое распределение;
- ручное назначение;
- очереди;
- команды;
- специализацию.

Возможные стратегии:

### Round Robin

Поочерёдное распределение.

### Least Loaded

Оператор с минимальной текущей нагрузкой.

### По компании

Например конкретные сотрудники работают только с определённым юридическим лицом.

### По каналу

Например отдельная команда Wildberries.

### По типу проблемы

Например:

AUTH → более опытный оператор.

### По severity

Критические сообщения → senior / supervisor.

Все правила должны настраиваться через UI.

# 12. Автоматические ответы вне рабочего времени

Если сообщение пришло вне рабочего времени, система должна иметь возможность автоматически ответить.

Например:

> Мы получили ваше сообщение. Команда вернётся с ответом в рабочее время.

Необходимо исключить повторение автоответа на каждое последующее сообщение клиента внутри одного диалога.

---

# 13. Режимы ответа

Система должна поддерживать три режима.

## 13.1. Полностью автоматический

Разрешается для безопасных случаев.

Например:

- 5★;
- отсутствует скрытый негатив;
- нет вопроса;
- нет претензии;
- нет риска;
- AI confidence выше установленного порога.

AI формирует уникальный ответ и автоматически публикует его.

---

## 13.2. AI Draft + Human Approval

Основной режим.

AI:

1. анализирует обращение;
2. создаёт ответ;
3. показывает его оператору.

Оператор:

- читает;
- редактирует;
- отправляет.

---

## 13.3. Human Only

Обязательно для определённых категорий:

- AUTH;
- RETURN;
- серьёзный DEFECT;
- MARK;
- юридический конфликт;
- угрозы;
- безопасность;
- сложная компенсация.

---

# 14. Уникальность AI-ответов

AI не должен использовать один и тот же шаблон механически.

При формировании ответа учитывать:

- содержание сообщения;
- имя клиента, если доступно;
- товар;
- историю диалога;
- предыдущие обращения;
- Tone of Voice;
- тип проблемы;
- контекст покупки.

При этом ответ не должен содержать неподтверждённых фактов.

Например:

# 26. AI-анализ каждого сообщения

Каждая коммуникация проходит AI-классификацию.

Пример:

```json

  "summary": "Клиент считает стойкость значительно ниже знакомого оригинала",

```

# 28. Скрытый негатив

Анализируются **все отзывы от 1★ до 5★**.

Пример:

> Всё отлично, поставил 5 звёзд, но аромат держится не больше часа.

Результат:

`rating = 5`

`hidden_negative = true`

`LONG = true`

Автоматический позитивный ответ в таком случае запрещён.

---

# 29. Severity

### P0

Критический.

Примеры:

- безопасность;
- потенциальный массовый инцидент;
- критическая маркировка;
- регулятор.

### P1

Высокий.

- оригинальность;
- серьёзный DEFECT;
- протечка;
- пустой флакон;
- неправильный товар;
- конфликт возврата.

### P2

Средний.

- стойкость;
- запах;
- упаковка;
- контент.

### P3

Низкий / позитив.

---

# 30. Объективные и субъективные сигналы

Система должна отдельно классифицировать:

### Subjective

Например:

- «не нравится запах»;
- «не стойкий»;
- «кажется неоригинальным».

### Objective

Например:

- распылитель не работает;
- флакон пуст;
- товар протёк;
- DataMatrix ведёт на другой товар;
- фактический объём неправильный.

Это важно для эскалации.

---

# 31. Хранение истории VoC

Все сигналы должны сохраняться на уровне:

`ProductID`

а не только конкретного кабинета.

При этом каждый сигнал должен сохранять исходный контекст:

- площадка;
- кабинет;
- SKU;
- дата;
- reviewId;
- orderId;
- rating;
- текст;
- signal;
- severity.

---

# 32. Основной показатель

Использовать:

> **VoC Signals per 100 Redemptions**

Например:

100 выкупов.

3 сигнала LONG.

Результат:

> `LONG = 3 сигнала на 100 выкупов`.

Если отзыв нельзя связать с конкретной продажей, запрещено интерпретировать показатель как:

> «3% покупателей пожаловались».

---

# 33. Rolling Window

Поддержать:

- последние 20 выкупов;
- 50;
- 100;
- 200;
- 30 дней;
- 60 дней;
- 90 дней;
- custom.

Для массовых SKU основным может быть:

> последние 100 выкупов.

---

# 34. Исторический baseline

Система рассчитывает обычный уровень каждого сигнала по каждому ProductID.

Например:

**Product A**

Исторический LONG:

> 2–5 / 100.

Текущий:

> 3 / 100.

Статус:

> 🟢 NORMAL.

---

# 35. Выявление аномалий

Правила выполняет обычный код / Rules Engine.

AI только классифицирует содержание.

Пример:

```text
CURRENT = 3%
BASELINE = 2–5%

STATUS = NORMAL
```

или:

```text
CURRENT = 9%
BASELINE = 2–5%

STATUS = ANOMALY
```

---

# 36. Возможные статусы продукта

`NORMAL`

`WATCH`

`ANOMALY`

`INVESTIGATION`

`CAPA`

`CONTROL`

`CLOSED`

---

# 37. Недостаточная выборка

Система должна учитывать размер выборки.

Например:

1 негатив / 1 выкуп = 100%

не должен автоматически означать массовую проблему.

Необходимо учитывать:

- количество выкупов;
- количество сигналов;
- baseline;
- длительность наблюдения.

Пороги настраиваются.

---

# 38. Cluster Detection

Помимо общего процента, система должна искать необычную концентрацию похожих сигналов.

Например:

обычно:

> 3 LONG / 100.

Но:

> 4 LONG за последние три дня.

→ `Cluster Alert`.

---

# 39. Тяжёлые единичные инциденты

Некоторые события эскалируются без ожидания статистики.

Примеры:

- пустой флакон;
- протечка;
- неработающий распылитель;
- неправильный товар;
- критический DataMatrix;
- безопасность;
- подтверждённое несоответствие.

---

# 40. Рекомендация оператору

Система должна непосредственно рядом с обращением показывать рекомендацию.

Например:

> LONG / AUTH  
> Последние 100 выкупов: 3 похожих сигнала  
> Current: 3%  
> Baseline: 2–5%  
> 🟢 Норма  
> **Ответить клиенту. Расследование не требуется.**

Или:

> 8 сигналов / 100  
> Baseline: 2–4%  
> 🔴 Аномалия  
> **Требуется расследование.**

---

# 82. Acceptance Criteria — коммуникация

3. получить AI-анализ;
4. получить AI draft;
5. изменить текст;

# 83. Acceptance Criteria — чат

После реализации chat-модуля:

1. клиент отправляет сообщение;
2. оно появляется в системе;
3. оператор отвечает внутри системы;
4. клиент получает его в исходном приложении;
5. ответ клиента возвращается в тот же thread;
6. полная история сохраняется.

# 86. Acceptance Criteria — серьёзный случай

система должна инициировать escalation независимо от текущего rate.

В журнале обязательно сохранить:

# 89. Главный принцип клиентского сервиса

Система не должна просто помогать **«ответить на отзыв»**.

Она должна понимать:

> **кто написал → по какому товару → что произошло → было ли это раньше → насколько это нормально относительно продаж → что мы уже знаем → как правильно ответить → требуется ли действие внутри компании.**

---

# 90. Главный принцип VoC

> **Каждое сообщение — сигнал.  
> Но не каждый сигнал — проблема.**

Система должна автоматически отделять:

**естественный клиентский шум**

от

**системного отклонения, которое требует вмешательства.**

---

# 91. Главный принцип разработки

При разработке через vibe coding нельзя создавать один большой монолитный кодовый блок.

Систему необходимо разбить на независимые модули:

```text
Integrations
Messaging
Inbox
Products
Orders
VoC
AI
Rules Engine
Incidents
Bitrix
Analytics
Authentication
Administration
```

Каждый модуль должен:

- иметь понятный API;
- иметь тесты;
- быть заменяемым;
- минимально зависеть от конкретного маркетплейса.

---

# 92. Ключевой итоговый результат

После запуска системы оператор должен работать примерно так:

> Пришло новое сообщение.

Он **не открывает кабинет маркетплейса**.

В едином окне он сразу видит:

- клиента;
- товар;
- заказ;
- площадку;
- историю;
- AI-анализ;
- проблему;
- статистику товара;
- норму;
- рекомендацию;
- готовый ответ.

Нажимает:

> **Отправить**

и клиент получает его именно там, где написал:

**Wildberries / Яндекс Маркет / Ozon / Telegram / WhatsApp / MAX.**

А если система видит реальную аномалию, она параллельно запускает внутренний процесс расследования.

Это и должно быть основным продуктовым результатом всей системы.
