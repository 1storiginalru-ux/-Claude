# Voice — клиентские коммуникации и Voice of Customer

Первая рабочая версия по [ТЗ 1.1](docs/specification.md): Django 5.2 LTS, Python 3.12+, SQLite, серверный интерфейс на русском языке. Внешние подключения по умолчанию выключены. Демо-данные отдельно помечены и защищены от внешних отправок.

## Быстрый запуск на Mac

Один раз установите [Python 3.12 или новее](https://www.python.org/downloads/macos/), затем откройте Terminal:

```bash
git clone https://github.com/1storiginalru-ux/-Claude.git voice-mvp
cd voice-mvp
bash start.sh
```

Скрипт сам установит библиотеки, подготовит базу и при первом запуске предложит создать логин и пароль. Затем откроется браузер. Для остановки нажмите **Ctrl+C**. При повторном запуске достаточно `bash start.sh` в папке программы. Пароль по умолчанию не создаётся, существующие данные сохраняются.

Подробная инструкция простым языком: **[Запуск на Mac](docs/MAC.md)**.

Для второго компьютера: **[Установка на другом Mac и перенос прежних данных](docs/SECOND_MAC.md)**.

## Ручной запуск для разработки

Из корня существующего checkout (в облачной среде `/workspace/-Claude`):

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python manage.py migrate --noinput
.venv/bin/python manage.py seed_demo  # необязательно; не создаёт пользователей
.venv/bin/python manage.py createsuperuser
.venv/bin/python manage.py run_dev
```

`run_dev` запускает локальный HTTP-сервер на порту 8000, worker исходящей очереди и polling включённых кабинетов. Ctrl+C останавливает только созданные этой командой процессы. Это режим разработки; встроенный сервер не предназначен для внешней эксплуатации. В облачной среде зависимости уже установлены в `/workspace/.venvs/customer-voice`; вместо `.venv/bin/python` можно использовать `/workspace/.venvs/customer-voice/bin/python`.

Для доступа нужен пользователь, созданный через `createsuperuser`. Общего пароля, автоматического входа и встроенных учётных данных нет. Сначала создайте реальную компанию, кабинеты, пользователей, команды и Membership в администрировании. Пользователь без Membership видит пустое пространство; администратор видит все компании. Для рабочих сотрудников используются роли supervisor, operator, quality, investigator и viewer. Администрирование доступно только superuser, одного `is_staff` недостаточно.

## Подготовленные возможности

- Inbox: поиск, фильтры по компании, каналу, кабинету, типу, рейтингу, статусу, оператору, severity и сигналу; фильтры негатива, просрочки и unmapped SKU. Назначение оператору, смена статуса, история сообщений.
- Ответы: редактирование, атомарная очередь в БД, ключ идемпотентности формы, статусы `Queued → Sending → Sent → Confirmed / Failed`, сохранение AI-черновика и финального текста, экспоненциальный backoff, ручной повтор и аудит. `Sent` означает принятие API; `Confirmed` выставляется после чтения опубликованного ответа с площадки.
- Адаптеры WB и Яндекс Маркета: отзывы, вопросы и ответы, пагинация, повторное получение без дублей, проверка публикации. Сохраняются все исходные поля обращений и ответов, фото и видео по ссылкам, сведения о товаре, покупке и статистике; доступны галерея, видео и выгрузка JSON. [Полные данные и дозагрузка прежних отзывов](docs/FULL_CONTENT.md). Чаты пока не подключены.
- ProductID, SKU нескольких кабинетов, атомарный импорт CSV/XLSX, проверки конфликтов и принадлежности компании; история изменений в аудите.
- Автоматические продажи/возвраты WB по отдельным событиям (включаются в кабинете, нужны права «Статистика»), история без дублей и окна последних 100 единиц. Для Маркета пока импорт дневных продаж CSV/XLSX. [Подключение, сверка трёх товаров и смысл метрик](docs/SALES_VOC.md).
- VoC: несколько сигналов, скрытый негатив, severity, объективность; окна ≥20/50/100/200 выкупов или 30/60/90 дней; недостаточная выборка, baseline, NORMAL/WATCH/ANOMALY, кластеры и независимая эскалация серьёзного объективного случая.
- Стойкость и сомнения в оригинальности объединены в группу с подсчётом уникальных отзывов; исходная разметка и Human Only сохраняются. Карточка различает долю негатива среди отзывов и сигналы на 100 выкупов, показывает полноту истории/классификации и отдельный кабинет.
- Tone of Voice по компании, загрузка TXT/Markdown/DOCX/PDF с текстовым слоем, отдельные подтверждённые знания. AI-провайдеры OpenAI/Anthropic со строгой проверкой структуры результата. Правила и разрешения выполняются обычным кодом. AUTH, RETURN, MARK, P0 и серьёзный DEFECT работают в Human Only без AI-черновика. Автоматическая отправка AI в этой версии выключена.
- Ручное подтверждение негатива независимо от AI, защита устаревших решений, очередь «Контроль товаров» с фильтрами и общей приоритизацией, правила общего негатива и отдельных кабинетов. [Рабочий процесс и настройка](docs/CONTROL_WORKFLOW.md).
- Расследования с ответственным, сроком, русскими статусами, неизменяемым снимком при открытии, гипотезой, действиями, результатом, связью с обращениями и дедупликацией `ProductID + signal + open incident`; ручная передача и обновление задачи Bitrix24.
- Авторизация Django, CSRF, экранирование текста клиента, срок сессии, разделение доступа по компаниям, аудит действий и согласованная резервная копия БД.

## Подключение кабинетов и AI

Для отдельного Ubuntu-сервера подготовлены PostgreSQL, Gunicorn, службы systemd,
проверка через SSH-туннель и перенос рабочей базы с Mac:
[инструкция серверного размещения](docs/SERVER.md). `start.sh` остаётся локальным запуском.

Ключи не хранятся в моделях или исходниках. В защищённых настройках среды задаются переменные; в карточке кабинета хранится только **имя** переменной. Для нескольких кабинетов используйте отдельные имена, например `VOC_WB1_TOKEN`, `VOC_WB2_TOKEN`.

| Компонент | Настройка | HTTPS-домен |
|---|---|---|
| WB | API-токен в переменной `VOC_WB_TOKEN`, поле кабинета `token_env` | `feedbacks-api.wildberries.ru` |
| Яндекс Маркет | API-Key в `VOC_YM_TOKEN`, Business ID в карточке кабинета | `api.partner.market.yandex.ru` |
| OpenAI | `VOC_AI_KEY`, provider=openai, точный доступный model ID в компании | `api.openai.com` |
| Anthropic | отдельный ключ или `VOC_AI_KEY`, provider=anthropic, точный model ID | `api.anthropic.com` |
| Bitrix24 | `VOC_BITRIX_DOMAIN`, `VOC_BITRIX_TOKEN` (OAuth), `VOC_BITRIX_OWNER_ID`, уникальный `VOC_BITRIX_NAMESPACE` | ваш портал `*.bitrix24.ru/com/by/kz` |

Включайте кабинет только после ввода корректных параметров и импорта Mapping. Демо-компанию для этого использовать нельзя. AI-профиль и модель настраиваются отдельно для каждой компании. Без AI-ключа выполняется **явно обозначенная предварительная разметка по ключевым словам**, confidence=0, без AI-черновика. Она не заменяет проверку оператором.

Bitrix24 получает только данные расследования. Перед созданием проверяется внешний маркер `XML_ID`, найденная задача обновляется. После неопределённого результата создание блокируется до сверки. OAuth-токен необходимо обновлять через защищённое окружение: автоматического OAuth refresh flow в MVP нет. Для одновременной передачи одной карточки используйте одного ответственного сотрудника.

Внешние API не проверены с реальными кабинетами: в исходной среде не было ключей, Business ID и данных портала. Контрактные тесты используют контролируемые ответы; они не подтверждают фактическую публикацию. Приёмку WB и Яндекс Маркета нужно завершить по [чек-листу](docs/acceptance.md).

## Импорт и корректность VoC

[Пример Product Mapping](docs/mapping-example.csv) и [пример продаж](docs/sales-example.csv) используют кабинет `WB1` и юридическое лицо `ООО Пример`, которые нужно заранее создать. CSV — UTF-8, разделитель запятая или точка с запятой. Excel — XLSX без формул. Лимиты: 5 МБ, 5000 строк. Для WB `SKU` и `External Product ID` — один и тот же числовой **артикул WB (`nmId`)**, а не артикул продавца. Для Яндекс Маркета `SKU` — **артикул продавца (`offerId`)**; если отдельного внешнего ID нет, его же можно повторить в `External Product ID`. В продажах WB используйте тот же `nmId`. [Подготовка широкой таблицы и обновление прежних данных](docs/PRODUCT_MAPPING.md).

Одинаковый ProductID означает один физический товар во всех компаниях и юридических лицах. При импорте описание товара должно совпадать. Аналитика объединяет его SKU в пределах компаний, доступных пользователю; администратор видит общую статистику. Rules Engine и расследования объединяют сигналы по каноническому ProductID. Истории обращений и Tone of Voice остаются ограничены правами на компанию исходного кабинета.

Дневные продажи не позволяют честно определить границу ровно сотого выкупа внутри дня. Поэтому окно ≥100 включает весь граничный день во всех кабинетах, а интерфейс показывает фактическое число выкупов и сигналов. Метрика — **сигналы на 100 выкупов**, а не процент покупателей. Точное окно по отдельным продажам потребует импорта событий выкупа с временными метками.

Baseline можно задать вручную в администрировании. После импорта продаж при достаточной истории рассчитывается исторический baseline за 90 дней **до начала текущего окна**, минимум 100 исторических выкупов; ручные значения сохраняются. Используется приближение Пуассона `n ± 1.96√n`, а при нуле сигналов — верхняя граница 3 события на историческую выборку. Это стартовая статистическая эвристика, требующая калибровки на ваших данных. Повторный расчёт:

```bash
.venv/bin/python manage.py calculate_baselines
```

## Фоновые процессы и восстановление

При раздельном запуске:

```bash
.venv/bin/python manage.py runserver --insecure --noreload 127.0.0.1:8000
.venv/bin/python manage.py worker
.venv/bin/python manage.py sync_channels --loop --interval 60
```

Каждая команда выполняется в отдельном терминале из корня проекта. Для однократной обработки поддерживаются `worker --once` и `sync_channels`. Автоматический опрос WB и Яндекс Маркета ограничен последними **7 сутками по дате создания отзыва или вопроса**, до начала текущего цикла. На каждом цикле окно сдвигается. WB получает записи от новых к старым, по 1000 на страницу; архив старше недели не запрашивается. Старые сохранённые позиции загрузки переключаются на недельное окно автоматически, без сброса пауз API. Для вопросов Маркета API принимает календарные даты, поэтому точная граница дополнительно проверяется по времени создания в ответе.

Фоновая дозагрузка полных данных и истории тоже работает только с обращениями последних 7 суток. Старые локальные записи сохраняются и доступны в Inbox, но автоматически не обновляются. Отправка ответа оператором и проверка публикации уже отправленных ответов продолжают работать, в том числе для старых обращений; это адресные действия, а не обход архива.

Для WB действует общий сохраняемый в БД бюджет запросов: polling, worker и ручная сверка одного ключа не обходят паузу друг друга. Учитываются `Retry-After`, `X-Ratelimit-Retry`, `X-Ratelimit-Reset` и исчерпание `X-Ratelimit-Remaining`. Если сервер не сообщает паузу, после HTTP 429 используется возрастающий backoff от 60 секунд. Состояние загрузки и время следующей попытки сохраняются при перезапуске. На странице «Интеграции» показываются полученное количество, статус ожидания и время, не ранее которого возможна следующая попытка. Реальный интервал зависит от лимита вашего токена WB и использования кабинета другими программами.

После пяти обычных отклонённых попыток ответ остаётся в Failed. Ограничение частоты оставляет ответ в Queued до разрешённой попытки; локальное ожидание бюджета не увеличивает счётчик HTTP-попыток. Неопределённые сетевые результаты и прерванный Sending автоматически не повторяются: повтор может создать дубль у площадки. Сверку выполняет руководитель: сначала поиск ответа через API, затем подтверждение отсутствия ответа в кабинете. Только после подтверждения разрешается ручной повтор. Нельзя обещать exactly-once для внешних API без соответствующей поддержки площадкой.

Состояние находится в `.local/`: SQLite, сессии, ключ Django. Оно исключено из Git. `VOC_STATE_DIR` позволяет выбрать другое постоянное хранилище. Резервное копирование:

```bash
.venv/bin/python manage.py backup_db
```

Копии создаются в `.local/backups/`; регулярное расписание, перенос в защищённое хранилище и проверку восстановления нужно настроить для production. Для восстановления остановите процессы и восстановите БД из выбранной копии, сохранив ключ Django и окружение.

Медиаданные отзывов хранятся в виде исходных ссылок API; файлы автоматически не скачиваются и не архивируются. В карточке обращения можно скачать весь полученный JSON и историю. Дозагрузка ограничена последними 7 сутками, даже если после миграции `0004` осталась позиция обхода всего архива WB. История Маркета дополняется ограниченной фоновой очередью с продолжением страниц после прерывания. В «Интеграциях» показаны период, общий размер локального архива и прогресс полных данных за 7 суток.

## Проверки

```bash
.venv/bin/python manage.py check
.venv/bin/python manage.py makemigrations --check --dry-run
.venv/bin/python manage.py test desk.tests
```

Тесты проверяют бизнес-правила, изоляцию компаний, права и CSRF, вход, рендеринг экранов, импорт и откат конфликтов, идемпотентность входящих, очередь, backoff, неопределённую отправку, сверку публикации, AI-контракты и Bitrix24. Внешняя сеть в тестах блокируется.

## Границы релиза

Это MVP для разработки и интеграционной приёмки, а не подтверждённая промышленная система 24/7. До внешнего использования нужны приёмка реальных API и модели, PostgreSQL и production process manager, HTTPS/reverse proxy с ограничением попыток входа, мониторинг, регулярные резервные копии и нагрузочные тесты. SQLite и один worker выбраны для воспроизводимой локальной среды; нагрузка в десятки тысяч сообщений не проверялась.

Ozon, мессенджеры, marketplace chats и их вложения, локальное архивирование медиа, автоматические ответы, advanced routing, рабочие расписания, подробные профили клиентов/заказов и QA относятся к следующим этапам ТЗ. Docker, Redis и Node.js для текущего режима не требуются. Облачная задача уже изолирована: используйте существующий checkout, без создания Git worktree.
